Introducción

Nuestra API está construido bajo los estándares de REST. Es decir, posee URLs orientadas a recursos y hace uso de los códigos de respuesta HTTP para indicar los posibles errores en ella. Para cada petición se encuentra implementada una autenticación HTTP (Bearer Token). Además, soportamos las solicitudes HTTP de origen cruzado (CORS), permitiendo que podamos interactuar con tu sitio de manera segura mediante nuestra API desde una aplicación cliente. Cada petición a la API retorna un objeto JSON incluyendo errores. Adicionalmente, nuestras bibliotecas convierten las respuestas en objetos específicos para cada lenguaje soportado.

Para que puedas comenzar a experimentar con nuestra API, todas las cuentas registradas en Culqi poseen llaves para el entorno de prueba (Regístrate y obtén tus llaves) y el entorno de producción. al usar las llaves de prueba, las transacciones no pasan por redes bancarias ni tienen costo ( Al probar, recuerda usar tarjetas de prueba).

Nunca debes exponer tu Llave Secreta en el código de la aplicación cliente web.
Tokens

Captura de manera segura los datos sensibles de las tarjetas de crédito y débito directamente desde el navegador de tu cliente sin que toquen tus servidores.

Cargos

Realiza un cargo o cobro a las tarjetas de crédito o débito de tus clientes usando un token de cargo único o una tarjeta que haya sido guardada previamente.

Planes

Define un plan que contenga información acerca del tipo de cargo, frecuencia, intervalo y monto que quieres cobrar a un cliente de manera recurrente.

Subscriptions

Realiza cargos recurrentes a tus clientes asociando una tarjeta de crédito o débito con un plan de suscripción creado previamente.

Clientes

Crear un cliente te permitirá asociar un usuario a una o varias tarjetas de crédito o débito para realizarles cargos recurrentes o pagos en un solo click.

Tarjetas

Guarda información de las tarjetas de tus clientes frecuentes para realizarles cargos sin que vuelvan a ingresar todos los datos de sus tarjetas de crédito o débito.

Autenticación

Culqi autentica tus solicitudes de API usando tu llave pública o privada. Se genera un error de petición si no incluyes una llave en la petición, y un error de autenticación si la llave es incorrecta.

Para poder acceder y utilizar nuestra API necesitas previamente obtener tus Llaves de Autenticación e incluirlas en cada petición que hagas. Podrás encontrar tus llaves en el Panel de Integración y Producción.

Ten en cuenta que es información muy sensible y no puedes compartirla con nadie.

Para usar nuestra API utiliza autenticación Bearer y envía el header Authorization como se muestra a continuación:

Ejemplo de autenticación:

curl --location --request POST 'https://api.culqi.com/v2/charges' \
--header 'Authorization: Bearer sk_test_UTCQSGcXW8bCyU59' \
--header 'Content-Type: application/json'

Las llaves secretas de integración tiene el prefijo 'sk_test_' y las llaves secretas de producción tienen el prefijo 'sk_live_'

Todas las peticiones al API deben ser hechas bajo el protocolo de transferencia HTTPS. Las llamadas hechas bajo el protocolo HTTP plano fallarán en el entorno de producción al igual que las peticiones sin autenticación.

Encriptación AES/RSA

Culqi proporciona un mecanismo de encriptación híbrido AES/RSA entre tus servidor y Culqi, ya que permite encriptar la data sensible del payload de los servicios POST y PATCH resguardando los datos en tránsito y brindando un segundo factor de protección, ya que cifra los datos y los protege contra cualquier acceso ilícito.

La data sensible del payload se encripta con AES-256-GCM (encriptación simétrica) con un “key” e “iv” generados aleatoriamente, luego se encripta el “key” e “iv” con la llave pública RSA (encriptación asimétrica) y el algoritmo “RSA/ECB/OAEPWithSHA-256AndMGF1Padding”.

El payload encriptado tiene formato json y consta de 3 parámetros:

encrypted_data: payload encriptado.
encrypted_key: key de la encriptación simétrica AES-256.
encrypted_iv: Vector de inicialización de la encriptación simétrica AES-256.

Para poder encriptar el payload de nuestra API necesitas previamente obtener tus llave RSA e incluir en el header el ID de la llave RSA en cada petición que hagas. Podrás generar tus llaves RSA en el Panel de Integración o Producción.

¿Cómo generar el payload encriptado?

Para generar la encriptación del payload debe seguir los siguientes pasos:

Almacena tu llave RSA y ID de la llave RSA en tu server.

Genera un key aleatorio(AES-GCM).

Genera un iv aleatorio(ASES-GCM).

Encripta el payload con el key e iv generados con el algoritmo AES-GCM.

Encripta el key aleatorio con la llave RSA pública.

Encripta el iv aleatorio con la llave RSA pública.

Genera el payload encriptado en formato JSON, el cual contiene el encrypted_data, encripted_key, encrypted_id.

Debes enviar en tu petición el payload encriptado.

A continuación mostramos un ejemplo de encriptación con Python:

import json
from Crypto.PublicKey import RSA
from Crypto.Cipher import PKCS1_OAEP
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes
from Crypto.Hash import SHA256
import base64

class RsaAesEncoder:

    def _encrypt(self, data, public_key):
        # Generate a random encryption key
        key = get_random_bytes(32)
        iv = get_random_bytes(16)

        # Message to be encrypted
        message = json.dumps(data).encode('utf-8')

        # Initialize the cipher with the key and IV
        cipher = AES.new(key, AES.MODE_GCM, iv)

        # Encrypt the message
        # Note that the message length must be a multiple of 16 bytes
        ciphertext = cipher.encrypt(message)

        encrypted_message = base64.b64encode(ciphertext).decode('utf-8')

        # Encrypt the key with the public key
        cipher = PKCS1_OAEP.new(RSA.import_key(public_key), hashAlgo=SHA256)
        ciphertext_key = cipher.encrypt(key)

        # Encrypt the iv with the public key
        cipher = PKCS1_OAEP.new(RSA.import_key(public_key), hashAlgo=SHA256)
        ciphertext_iv = cipher.encrypt(iv)

        # Convert the encrypted message to a string
        encrypted_aes_key = base64.b64encode(ciphertext_key).decode()
        encrypted_aes_iv = base64.b64encode(ciphertext_iv).decode()

        return {
            "encrypted_data": encrypted_message,
            "encrypted_key": encrypted_aes_key,
            "encrypted_iv": encrypted_aes_iv
        }

Metadata

La metadata es una manera útil de guardar información adicional de manera estructurada en un objeto. Nuestros recursos, incluyendo Tokens, Cargos, Planes, Suscripciones, Devoluciones, Tarjetas, Clientes tienen un parámetro metadata que puede ser utilizado para reflejar información clave del negocio que quieras relacionar con las operaciones.

Por ejemplo, en el parámetro metadata del recurso Clientes podrás guardar el nombre completo de tu cliente, su número de documento de identidad y su fecha de nacimiento. La metadata no es utilizada por nosotros para analizar, realizar o rechazar un cargo.

El atributo metadata no puede tener más de 20 objetos clave-valor. Adicionalmente, la clave no podrá exceder de 30 caracteres y el valor de 200 caracteres.

Ejemplos de metadata


Por ejemplo, en la petición para crear un cargo al API, podrás enviar los valores como user_id , user_details a través del objeto metadata:

    "order_id": "204055",

Paginación

Todas nuestras APIS soportan operaciones de listado, entre ellos tokens, cargos, tarjetas, clientes, suscripciones, devoluciones y planes. Adicionalmente, todos los métodos de listado comparten una estructura similar tomando en cuenta estos tres parámetros: limit, after y before.

Utilizamos una paginación en tiempo real basada en cursor a través de los parámetros after y before. Un cursor se refiere a un string de caracteres random que marca un ítem específico en una lista de datos. A menos que el ítem sea borrado, el cursor siempre estará punteando la misma parte de la lista, pero será invalidado si el ítem es removido.

Los parámetros after y before toman el valor ID y retornan los objetos en un orden cronológico reverso. El parámetro before devuelve los objetos creados antes del objeto en cuestión. El parámetro after devuelve los objetos creados después del objeto en cuestión. Si ambos parámetros son provistos solo before es utilizado.

ID de rastreo

Cada petición al API está asociada a un identificador de rastreo. Puedes encontrar este valor en los headers de respuesta, bajo el nombre de x-culqi-tracking-id, en el Panel de Culqi y en el detalle de cada petición.

Si necesitas ayuda con alguna petición en específica, al brindar este ID de rastreo, será más fácil la ubicación y posterior solución al problema o incidencia.

Tokens

Tokenización es el proceso que utiliza Culqi para capturar de manera segura datos sensibles de tarjetas de crédito y débito directamente desde el navegador del cliente. Un token representa a una tarjeta dentro de nuestro flujo de pago y es devuelto a tus servidores para que puedas utilizarlo a través de Culqi Checkout o nuestras bibliotecas para móviles (iOS y Android). Este método nos asegura que ningún dato de la tarjeta toque tus servidores y permite que la integración cumpla con la normativa PCI DSS.

Recuerda que la forma más sencilla de cumplir con la normativa PCI es nunca ver (o tener acceso a) los datos de la tarjeta.

Si no deseas hacer uso de los métodos de tokenización disponibles, también puedes crear tokens utilizando la API y tu llave pública. Pero, ten en cuenta que cuando pasas la información de las tarjetas directamente a la API de CULQI, tu integración se encarga directamente de esos datos y debes demostrar anualmente el cumplimiento de todos los controles de seguridad que exige la normativa PCI (SAQ-D).

¿Qué es el SAQ-D?

El SAQ-D (Self-Assessment Questionnaire D) es una herramienta que permite conocer a las marcas (Visa, MasterCard o American Express), el nivel de cumplimiento del comercio con respecto a los requisitos de seguridad de PCI DSS. Es aplicable para todos los comercios que aceptan datos de tarjeta en sus propios sitios web y/o los almacenan electrónicamente en sus propios servidores.

Quiero usar la API de Culqi ¿qué debo hacer para cumplir la normativa PCI?

Debido a que el cuestionario trata sobre requisitos de seguridad, recomendamos que el documento sea revisado en compañía del responsable de tecnología y/o de Ciberseguridad.

Lo primero que debe hacer el comercio es descargar el cuestionario “SAQ D Merchant" del siguiente enlace.

El comercio deberá revisar las instrucciones del documento y dar respuesta a todas las secciones del documento (sección 1, sección 2 y sección 3).

La "Sección 1" trata sobre el modelo de negocio del comercio.

La "Sección 2" habla sobre los requisitos de seguridad para la protección de los datos de los tarjetahabientes, para ello, existen 5 opciones de respuesta, cada requisito debe tener al menos 1 opción de respuesta: (1) Implementado (2) Implementado con CCW, (3) No Aplicable, (4) No Probado y (5) No Implementado.

La "Sección 3" es una declaración de conformidad que deberá completar y firmar el representante legal del comercio

Luego de completar todas las secciones del documento, el comercio deberá enviar el documento al equipo de Seguridad de la Información de CULQI (pci-compliance@culqi.com)

El equipo de Seguridad de CULQI revisará el documento enviado y dará su conformidad al comercio. De encontrar alguna observación retomarán con el comercio para que puedan subsanar el hallazgo.

Puntos a tener en cuenta:

Por política interna de CULQI, solo podrán hacer uso del SAQ-D los comercios que no han sobrepasado los 5 millones de transacciones anuales.

El SAQ-D es un documento obligatorio para los comercios que quieran usar la API de CULQI. Los comercios no podrán afiliarse sino completan y envían el documento.

Si el comercio ha sobrepasado los 5 millones de transacciones anuales, las marcas de pago (Visa, MasterCard y American Express) considerarán al comercio como proveedor de NIVEL 1, lo que implica que el comercio deberá presentar un informe anual de cumplimiento (ROC) y obtener su certificación de cumplimiento PCI (AOC).

Quiero certificar mi comercio en PCI ¿Qué debo hacer?

El primer paso para iniciar el proceso de certificación de PCI es mediante un assessment que permita identificar las capacidades y brechas con respecto al cumplimiento de todos los requisitos de la norma PCI.

Para ello, el comercio puede iniciar un assessment interno, realizado por sus propios especialistas de la organización o contratando los servicios de un auditor externo certificado en PCI DSS.

Luego de obtener los resultados del assessment, el comercio debe implementar todos los planes de acción producto del assessment. Esto involucra contratar servicios, comprar herramientas y formalizar procesos y procedimientos.

Cuando el comercio esté preparado para una auditoría externa, debe contactarse con una empresa auditora que brinde el servicio de auditoría externa PCI. Esta empresa debe tener la capacidad de emitir un AOC y esta debe renovarse anualmente.

Eventos

Cuando algo sucede en tu cuenta, creamos un objeto evento como una forma de comunicártelo. Por ejemplo, cuando un cargo es exitoso, habilitamos el evento charge.succeeded. Adicionalmente, si realizas muchas peticiones al API podría llegar a causar multiples eventos. Es decir, si creas una suscripción para un cliente, recibirás el evento customer.subscription.created y el evento charge.succeeded.

Al igual que los otros recursos del API, puedes consultar un evento particular o listar una serie de eventos directamente desde ella. También, hemos construido un sistema automatizado que enviará eventos directamente a tu servidor: webhooks. Reconedamos que revises nuestra guía de webhooks para que sepas cómo configurarlos.
